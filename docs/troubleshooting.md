# Surge 排错手册

## 先确定问题层级

```text
Surge 是否运行？
  ↓
请求是否被捕获？
  ↓
规则是否命中？
  ↓
策略组是否选对？
  ↓
节点/DNS/目标站点是否正常？
```

不要在没有确认上一层的情况下直接修改规则。

## Surge 没有捕获请求

检查：

- Surge 是否已启动；
- iOS VPN 或网络接管状态是否正常；
- 当前 Profile 是否加载成功；
- App 是否使用了自己的网络实现；
- 是否只有某一个 App 失败，还是所有流量都失败。

## 规则没有生效

检查：

- 域名是否写成了正确的 `DOMAIN` 或 `DOMAIN-SUFFIX`；
- 规则是否位于 `FINAL` 之前；
- 外部 Rule Set URL 是否可以访问；
- Rule Set 文件中是否误写了策略名称；
- 请求实际使用的主机名是否与你添加的域名一致；
- Surge 是否仍在使用旧缓存。

规则按顺序第一条匹配生效，很多“规则失效”其实是前面已有更宽泛的规则抢先匹配。[Rules Overview](https://manual.nssurge.com/rules/overview.html)

## 节点无法连接

先把策略组切换到 `DIRECT` 测试目标是否本身可访问，再单独测试节点。记录：

- 节点协议和端口；
- DNS 解析结果；
- 网络环境；
- 节点延迟或连接错误；
- 是否只有某个节点失败。

不要通过不断增加规则来解决节点本身不可用的问题。

## DNS 问题

区分三种情况：

- 域名无法解析；
- 域名解析到了错误地址；
- DNS 正常，但后续连接失败。

先用 Surge 的 DNS 查询或请求信息确认实际解析链路，再决定是否修改 `[General]` 或 `[Host]`。

## GitHub 规则更新没有生效

按顺序检查：

1. GitHub 文件是否位于正确分支；
2. Raw URL 是否可访问；
3. 文件内容是否为纯文本；
4. 规则格式是否正确；
5. Surge 是否已到达更新间隔；
6. 规则是否被缓存；
7. 请求是否真的命中了该规则集。

必要时先修改一个明显但安全的测试规则，确认更新链路，再恢复正式内容。

## 出现大面积断网

优先回滚最近一次规则或 Profile 变更，恢复到已知可用版本，再逐条分析差异。不要在故障状态下同时修改 DNS、策略组、Rule Set 和 MITM。
